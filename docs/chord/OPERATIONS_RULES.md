# CHORD GNSS stack: operating rules

What bit us and the rule it left: the companion to [CHORD_GNSS_RUNBOOK.md](../CHORD_GNSS_RUNBOOK.md), which says how to run the stack and is not repeated here. Consolidated 2026-11-04 from the memory files listed at the end. Dates are the incident's; hashes are on kv/chord-gnss unless named otherwise. Node log: `/tmp/gnss_node.log` on the node; broker log: `/var/tmp/gnss-logs/broker.log` on the VM (runbook §8).

## 1. Restarts and ordering

**choco maintenance mode ON for the six GNSS nodes before any fleet start.** 09-14, with it off, choco's per-minute sweep `GET /kill`ed every node within ~60 s of coming up, twice; nothing here sends `/kill`, and the last log line reads `ERROR: /kill endpoint called`. `ssh choco /usr/local/bin/choco nodes` shows MAINT per node; `choco maint on cx` sets it; start, stop, push and maint off are KV's call.

**After an F-engine re-base: refresh chive, then the nodes. frame0 is latched once per process, nodes and broker alike.** 09-14: chive served Saturday's epoch, every node logged `SEQ AXIS IS 134042 s FROM THE WALL CLOCK`, the broker had 0 rows. 09-16: the nodes relaunched onto a new epoch and the broker kept a 29.0 h stale anchor for 12 h (7 of 8 chains `0 present`) while its own detector logged `TIME ANCHOR CHANGED` 5960 times into a 2.2 GB log; a log-only monitor is not a monitor, so it now exits 3 after 3 confirmations (9c56c1682; `os._exit`, since broker_multi catches SystemExit per chain). Before any node start compare node utc with the wall clock (healthy ≈ −100 ms; formula in runbook §4), poll chive twice, and remember its raw `frame0_ctime` is 1024 GPS weeks behind by design.

**Diagnose an F-engine outage from the first error in `fpga_master.log` and the nodes' packet counters, not from the controller's steady state or its "started" line.** Logs under `/mnt/cs00/data/chord_pathfinder_f_engine_data/data/current/` (the symlink repoints on restart: copy first). 08-08: the first error was `No route to host` = ARP, boards off the net (`ip neigh` FAILED), not the hours of `Broken pipe`; fpga_master never reconnects, and `prog: 2` reprograms all 16 FPGAs, moving frame0. 09-21: a clean `Finished fpga_master.start()` while the F-X switch had errdisabled its ports for ~2 h; on `<node>:12048/metrics` (12048, not 12049), polled twice: `nic_link_up` 1, `nic_rx_packets_total` rising, `distributor_packets_total` 0 (healthy ~1.17 M CRS pkt/s per node).

**After a re-base, restart the nodes only after the broker's anchor (`starting 8 chain(s)`, `receiver clock BOOTSTRAP`), on a clean sky, outside transits.** A node whose first shared element model forms on old-epoch seeds pins `_g_pin_ref` on noise (09-28: cross-instance R pol0 E6 0.15, fleet_xcoh −0.066); the nodes' own relaunch beats the broker's ~3 min anchor on every re-base, and #154's fleet-reference pin did not heal it (10-08). Check `fixtures/fix0928/canary/snap_xinst.py` (R ≥ 0.95 every band) before a node_up loop. After an F-engine gain change the reference stops describing the models (10-08: sim 0.17); re-snapshot it (10-09, 701401e96) after reading `fixtures/obs/elem_ref/ALERT` and `auto_ref.json`.

**After any long node outage, restart the broker once the nodes are back, re-base or not.** 10-01: nodes down ~5.5 h with frame0 unchanged; the broker dead-reckoned every held code phase and slewed back at 0.05 chips/step, E23/E31 still ~20 chips off 20 min later, Galileo PVT hundreds of metres out, and it looked like a transit problem. Restart outside a transit freeze, then the CHAIN DIED check. Automatic since 10-26 for a whole-fleet outage ≥ 1200 s (runbook §5).

**Never restart the broker within ~10 min of an aggregator restart (#211).** 10-19, broker 87 s after the aggregator: the cold search had no overlay labels, gps_l5 seeded 2,634 chips off, every model-primary chain slewed +1.35 chips into the +3.0 trim clamp and sat on grating lobes (95 m = 3.27 chips) for ~30 min while presence and q never dropped. Cycle the aggregator alone, or wait for its LABEL CONSENSUS lines to quiet; judge restarts by obs `code_resid_m` (multiples of 95 m) and `dll_trim_cpp`.

**After every broker restart, at T+60 s and again ~240 s: `CHAIN DIED`/`Traceback` = 0, and gps_l5 has logged `receiver clock BOOTSTRAP`.** Chains are threads, so a dead one leaves the unit active (09-28: gps_l5 died on cycle 1, 2 min 40 s dead after reviewers and mid-stream replays had passed it; 10-18: only L5 locked for 16 min, `DRCLK clk_now 0.000`). `nice tail -c 40000000 /var/tmp/gnss-logs/broker.log | awk '/\] starting [0-9]+ chain/{b=""}{b=b"\n"$0}END{print b}' | grep -a -c -E 'CHAIN DIED|Traceback'` and `tail -n 20000 /var/tmp/gnss-logs/broker.log | grep "receiver clock BOOTSTRAP"`. #200 fixed 10-24 (af94c1b19). A first-cycle change needs a live restart, not a replay.

**Stagger node rolls: one node costs nothing, a fleet-wide roll ~30 min of L5.** 09-10: cx43 out 30 min, readback trims unchanged; the fleet roll pinned trims at the ±3.000 clamp 02:18-02:24, baseline at 02:38, because the standing C++ trim lives on each node. Judge a fleet cycle at t+30, elevations first.

**After F-engine, cabling or switch work, compare every GPU's tap `freq_ids` with the config before judging the sky (#194).** 10-17: four GPU-1 combs came back permuted against `gpu_offsets_mod16`; cx19.1 and cx51.1 despread nothing for an hour while `FLEET-INST` counted them present and `get_elem_cal` showed `chan_norm applied=false, miss` climbing. Check `rf_stats.freq_ids[0]` against `gnss<g>_n2assemble.channel_ids[0]` per instance; `config/gnss_fleet.py combs` reads the combs from the frames (af12c4220, runbook §5).

**A node restart reverts its slot→PRN map to the config list; the broker resyncs it, and a silent node has no veto.** 10-07: cx19's restart left BeiDou on C19-C42 against the fleet's C56/C58 and the stage froze on the split for five hours; d1ab60368 resyncs to the last-posted map or a strict majority, and 970db6bf5 (10-24) decides on the endpoints that answered. Check the `PRN MAP` heartbeat (every 15 min per chain).

**Do not restart anything whose start-up needs a node while the nodes are down; after any stack restart read `NRestarts`, not `active`.** 10-13: the eight `gnss-obs@*` writers failed on `cx43:12048/telescope/time0_ns` and relaunched 346 times in 70 min, re-importing numpy over NFS each time: VM load 23, a `git push` hung 27 min, `list-units` said active. `systemctl --user show gnss-obs@x -p NRestarts -p SubState`; D-state commands (`rpc_wait_bit_killable`) with no CPU user are a restart loop.

## 2. Nodes

**`scripts/gnss/site/node_up.sh <node> restart` runs as the user from `~/gnss/kotekan`; never `sudo` it.** It escalates on each node itself (KV, 09-29); a leading sudo runs its ssh and rsync as root with the wrong keys. Only a node_up start carries the unit's properties (runbook §5).

**An unexplained node restart: read `/tmp/gnss_node.log`, not the journal; a 06-07Z one with no FATAL, no core and `NRestarts` 0 is unattended-upgrades plus needrestart.** cx19 10-07 06:37Z (libfreetype6, which kotekan maps): two `Kotekan version` lines in the node log and `/var/log/dpkg.log` at that minute; node_up.sh writes `/etc/needrestart/conf.d/gnss-node.conf` since 16f82b73a, by hand `echo '$nrconf{override_rc}{qr(^gnss-node\.service$)} = 0;' | sudo tee /etc/needrestart/conf.d/gnss-node.conf`. 09-29: `malloc(): unaligned tcache chunk detected` just before the new `Kotekan version` line on cx51, cx43 and cx42 (`grep -a -c "malloc()" /tmp/gnss_node.log*`; journal status 6 is an abort, 11 a segfault). Either way the relaunch loses every REST switch, so what must survive one belongs in the config (`elem-proj-mode` became a manifest key). A core needs `kernel.core_pattern=/var/crash/core.%e.%p.%t.%s` per boot plus the unit's `LimitCORE` (~44 GB, root 0600). #153's cause: ring metadata replaced every frame by `cudaRFISKtilde` and read unlocked, plus a prefetcher race (#1713); fixed 10-01 (2aac0bc53, 1c6079daf).

**The #60 node wedge is DPDK ring starvation, not the GPU; `scripts/gnss/node_wedge_probe.sh` shows it without a restart.** 08-15: GPU idle at 0 %, ring drops in the hundreds of millions, dpdk-worker3/4 in state S at ~3100 ticks (healthy: R, ~257000): a worker lcore had died on a false positive, the sampled sequence check comparing different boards through one scalar. Fixed c80dc17ea (`kotekan_dpdk_workers_active`/`_expected`, `exit_on_worker_failure` default true, a whole-telescope change) and caba685a8. A restart does not clear it, and the production N² on that GPU stops too.

**Judge a node canary by per-core load on the pinned pools, not the process total.** 10-20 at 96 elements: total +0.8 core, no thread above 25 %, but the one core per GPU holding every chain's GnssGpuRecordAssemble (33, 57) read 99-100 % and four nodes stopped together on the next recv1 stall. Sum thread CPU by core (`/proc/<pid>/task/<tid>/stat` field 39); every non-DPDK pinned core < ~70 % over ≥ 10 min, a bright conjunction included.

**cf06 reboots near 03:03Z whenever a kernel lands, wipes `/tmp`, and nothing there restarts.** Since 09-17 that is only the cube leg (09-25: down ~12 h): `cubearch_up.sh`, then `cubecompact_up.sh` and `beamview_up.sh` (CHORD_BEAMCUBE_RUNBOOK.md §2); auto mode blocks starting them over ssh. Count with `pgrep -fc "[c]ubecompact_loop"`; `pgrep -af | wc -l` counts its own ssh shell.

## 3. The VM

**The Claude session runs on the production VM (`gnss`: 6 cores, 7 GB, one L40S in use): no heavy analysis there, `free -m` before any python, and subagents count.** 10-23: a 7.8 MB obs JSON loaded twice on the VM died rc 137 and the broker (1.6 GB resident, MemoryMax 3 GB) died silently at the same seconds, NRestarts 2; `nice` does nothing for memory. 10-08: six parallel subagents grepping the NFS tree held load ~33 for 30 min and the broker dropped 8 rows as `pow_hop in the FUTURE`. Below 2 GB available, or for anything that loads a dataset, use cf06 (64 cores, both L40S idle) or cf05 over the same NFS; on the VM only REST reads, greps and bounded tails.

**The cron list is the runbook's [Scheduled jobs](../CHORD_GNSS_RUNBOOK.md#scheduled-jobs); `crontab -l` before installing (an install replaces the table; `crontab - < file`), and the EOP and bad-input jobs patch running nodes only.** Since 10-11 (#173) `eop_cron.sh` regenerates `config/generated` when the staged table ends later and `gen_fleet --check` passes. Nothing pages: `ls fixtures/obs/{health,elem_ref}/ALERT`.

**The EOP table is inside the kotekan config, a 6-entry ~5-day window from `choco:/var/lib/choco/eop/state.json` (daily 12:00Z; moved there 09-08); it must contain `now`, and a push is a 5-day fuse.** 08-19: the base-captured table ran 18.1 days past its end, dUT1 was 5.007 ms wrong and recv1's hdf5 writer died; cx19's 17,085,672 `Requesting EOP later than in table` warnings (#68) had been filed as noise. 09-24 00:00:00Z: the live table ran out and every node FatalError'd at once. Checks: the span contains now; `grep -c "Requesting EOP later than in table" /tmp/gnss_node.log`. Live: POST the file to `http://<node>:12048/earth_rotation_data` and read the HTTP code. `node_up.sh` refuses below 12 h of headroom; regenerate before the end, reading the generator's warnings rather than a `tail` of them (08-28).

**Auto mode blocks node-config regeneration, cf06 service starts over ssh, live REST writes and force pushes: hand KV the exact command before touching shared state, and never work around a block.** Blocked 09-25..10-19: `gen_fleet.py config/gnss_fleet_chord.yaml`, `ssh cf06 cubearch_up.sh`, a POST to `/fleet_trim/set_policy`, `git push --force-with-lease`, foreground `sleep`; allowed: gather-config regen, `systemctl --user restart`, cf06 analysis, fast-forward pushes. A block mid-procedure leaves a half-applied state.

**`claude-screen.service` (user unit, 10-14) resumes the Claude sessions at boot**, one screen window per line of `~/.config/claude-screen/sessions` (`claude --resume <id> --remote-control <name>`). KV runs the enable; `install_user_units.sh` does not install it.

## 4. Builds and deploys

**Never relink kotekan in place on NFS while something runs it; build to a staging name or `mv` the running file aside first.** 08-31: an in-place relink under six running nodes; cx27 and cx43's gpu1 N2 path stalled within 2 min and FATALed 3 h later, and NFS gives no ETXTBSY across hosts (09-09, the cf06 gather). `ls -l /proc/<pid>/exe`: `(deleted)` is safe, a clean path is borrowed pages. Safe: `cp kotekan{,.next}` and swap at the restart, or `mv kotekan kotekan.prev_<ver>` then relink.

**A kotekan binary's RUNPATH points into its build tree (libn2k): build node binaries in an NFS dir that outlives the deployment, `ldd` them on a node that did not build them, and never delete a build dir without checking every live binary's RUNPATH and `/proc/<pid>/maps`.** 10-01: a cx19 `/var/tmp` build crash-looped cx51 on exit 127 (`libn2k_dual.so: cannot open shared object file`) while `ldd` on cx19 passed; build into `~/gnss/builds/fleet-<sha>` with `-DCMAKE_CUDA_COMPILER=/usr/local/cuda/bin/nvcc`. 10-12: `builds/gather-2d852b79e` was deleted as unused by argv, and the next gather restart died at exec (`libn2k.so`), broker blind ~10 min. `readelf -d <binary> | grep RUNPATH`; `grep -E 'builds|-wt' /proc/<pid>/maps | awk '{print $6}' | sort -u`.

**`config/generated/` is untracked since 10-08 (035bbb4e7): `gen_fleet.py <manifest>`, then `--check`, nothing to commit.** The files stay on disk for the nodes, gather, aggregator and archiver; the j2 vars went 10-13 (8130b25d5). Gather and archiver configs regenerate from their REGENERATE WITH headers, the aggregator from `scripts/gnss/site/agg_up.sh`; keep `config/base/live_config_20260730.json`.

**A new SignalDescriptor goes in the header, `gnssSignal.hpp` `signal_by_name`'s list, the replica dispatch and the broker's `signals.py`; before deploying a new chain, run the new binary on one node's new config and watch 60 s.** 10-20: SBAS_L5_Q_MC passed boost, the CI batches and the broker goldens, then killed cx51 at four launches (`unknown signal`); the broker started the chain anyway and the obs writer died on `--sys` G/E/C/R. Guard `python3 -m gnss_broker.test_signal_table`; a preview is not a run.

**A bash script running from the NFS checkout dies (`Stale file handle`) when another host updates the checkout: restart such loops after every release sync, or run them from a copy.** 11-03: cf06's `cube_staging_loop.sh` died after the release was pulled on the VM; bash reads in chunks and git replaced the inode. Python is read once and safe.

**CUDA streams are not free parallelism: 2 copy engines per GPU cap DMA, and compute streams alias onto `CUDA_DEVICE_MAX_CONNECTIONS` (default 8, max 32); we run nine kernel streams per GPU with it unset.** cx43 09-15: rxpci 13-18 GB/s all on stream 0, txpci 1-3 GB/s over 15 streams. An explicit `cuda_stream` is absolute while `cudaSyncInput`/`cudaSyncOutput` wait on the base: a copy pinned outside its stage's triple is waited on by nothing.

## 5. Data and files

**`~/.cache/kotekan_gps` is the live broker's BRDC store; nothing else writes it.** 10-08 01:34Z: the nightly cube build's `fetch_brdc(<day> 12:00Z)` pruned it: `PREDICTION COLLAPSE`, only noise probes for 45 min (#159); gps_l2c's clock latched +10 ms (#161) and only stop broker → restart aggregator → start broker cleared it. Noise-probe-only rows fleet-wide: check the broker log for PREDICTION COLLAPSE and the store's newest toc; the health cron cannot see it.

**Telemetry v5 and v6 cannot mix: nodes, gather and broker move together, and v5 captures do not replay against the v6 fold.** v6 (09-09) ships per-sender rows (GAL 20, rest 14) and columns; the fleet-wide constants before it padded L2C 62 % and silently dropped Galileo PRNs ("PRN 34 onwards", 1200+ windows), indistinguishable from a satellite setting. Needs `bufferRecv` `allow_short_frames` (01440c0cd); watch the packer's overflow WARN after any change.

**Stream-health rows are named by band from the frame's absolute `freq_id` and a declared set (broker `--rf-bands`), never by lobe index or nearest carrier.** With 8 chains, index 2 was L2C on 5 instances and B3I+E6 on 7; nearest-carrier named cx19/gnss1's 1199-1202 MHz channels GLONASS "L3", which CHORD does not fly. No declaration, no name; "5/12" on L2 is correct. After a tap restart, cx19/gnss1 must report L2C as freq_id 6284 and gnss0 none (b53cc962f).

**An artifact nothing regenerates and no gate can fail is a souvenir; a filename grep is not a reference check.** 09-02: the j2 vars were 107 lines stale under a README calling them authoritative; `node_up.sh` defaulted to a pre-E5a config that starts green with six chains missing (the manifest now names it); the six running `config/generated/chord_gnss_cx*_multi.yaml` matched nothing because `gen_fleet.py` builds the names at runtime. Ask what builds the name before deleting; a WHERE flag (`--out`) must not land in a REGENERATE WITH line.

**Node `dll_spacing` and broker `--dll-spacing` must match, nodes first; when the combiner changes, re-derive the discriminator's S-curve before judging the loop.** A mismatch is a pure gain error (4× at 2.0 vs 0.5). 09-02: L2C's one 195 kHz channel per instance caps q at 1.11 for a perfect lock at 0.5, so 2.0 shipped; 09-08 the lobe combine made it a 5-channel Dirichlet (null 0.52 chips) and fleet_q flapped 1↔40-100 with false locks at ±0.5 chips until 0.4. q "too good" (46 vs 5-7) is taps in nulls. Sweep `e2e.cf06 --signal GPS_L2C_CM --skip-search --t-nchan 5 --t-chan0 6284 --t-stride 1 --dll-spacing D`. The never-locked bug before it (2fe49e77f) was a unit; the tell was `ph@ref 11011.3` on a 10230-chip code.

## 6. Judging health

Runbook [§3](../CHORD_GNSS_RUNBOOK.md#3-is-it-healthy-four-numbers-one-minute) gives the four numbers; these are the ways they lie.

**Judge go/no-go in minutes, paired in time; never soak.** Records are 10.49 ms, broker cycles 2 s, the longest legitimate wait ~15 s. 08-21: arms judged on 45 min to overnight windows while the C++ code loop had been dead since the 20:09 F-engine restart, visible in one poll pair of `/fleet_trim/get_dll`; the averages hid it. Before any wait name what evolves, by what process, with what time constant, and how you will know. Exception (KV 10-25): an event-driven latch gate may soak with coverage criteria stated up front.

**Nothing is per-node or per-instance: an instance is `freq_id mod 8` routing after one PFB, instances run in lockstep, and a mismatch between them is a bug.** Never A/B by GPU or instance (`--carrier-phase-mode ab`, `--carrier-phase-from-ref ab`: NOT SAFE); one arm fleet-wide, paired in time. 09-06 the cube builder summed instance-local bins into 7 fake subbands (da9ac8418); 09-25 "cx42.0's L5 rail problem" was freq_id 6069 railing in 3.8 % of quiet passes. Make the per-freq_id spectrum first.

**A broker restart rails the gps_l5 fast loop for ~10 min (~30 after a re-base): in that window only the READBACK's decay is evidence, never its amplitude.** Trims swing to the ±3 clamp every 30 s; 09-08 the lobe combine was reverted at t+11 min on this, and the old loop then did the identical dance. Freezing the loop made it worse (#106: 14-38 % of rows above q 2.2 frozen vs 57-95 % live): the seeds are settling and the loop is absorbing a real common-mode offset above 3 chips. Shrinking `dead-reckon SLEW ... model-held` offsets are converging; do not restart. Normal readbacks: L5 0.10-0.26, L2C/E6 < 0.3, B2b/B3I 0.40-0.50 chips. The aggregator's post-re-base `sample_seq went BACKWARDS` needs no restart; C/N0 ±30 dB per PRN is elevations first.

**A gather restart keeps the standing trims (trim store since 08-24; re-measured 09-27, unchanged to 0.08 chip); it costs one fleet-ADR arc break while the 89 senders reconnect (~30 s).** Adoption is gated on arming, not done at load: `offered > 0` with `adopted == 0` under `trim_store` in `/fleet_trim/get_stats` is the alarm. A broker restart leaves the trims at the trackers (runbook §4).

**Never run `gate.sh` beside the live stack, and never call the fleet healthy on verdicts a dead gather satisfies.** 09-14: three gate.sh runs on cf06 starved the broker's receiver and the gather died with no FATAL; "stale 0" and "N armed" still passed, because a dead gather reads `nothing yet` and every trim POST was refused (`0 posts / 1349 failed`); seven chains ran on the standing policy. Non-vacuous: `TELEM up frames N` rising, `FLEET-TRIM ... N posts` rising, `FLEET-TRIM READBACK` lines. `gate.sh` now refuses beside a live stack (`GATE_FORCE=1`).

**q = 2P/(E+L) is peak sharpness, not SNR; the weights are `chan_noise_norm` (1/rms over the beam's own inputs), so judge a weight change by q and `chan_norm.w` on `/get_elem_cal`, not by taps or spectra, which are energy-normalised.** 10-08 (#163): E6 q 3.65 → 2.47 after `digitalgain_20261007T213936Z`; until a79daf533 (10-12) the weights were the digital gains. Low q with strong p and ~0 disc is shape: xcoh first, then per-instance `gnss<g>_<band>_n2combine/get_status`. Average over the beam's inputs: all 128 let the RFI antennas dilute the weights ±10 %.

## 7. Working habits that matter operationally

**Kill by the PID saved at launch; never `pkill -f` or `pgrep -f` a pattern that is on your own command line.** The Bash tool runs `bash -c '<command>'`. Cost so far: the tool shell killed (exit 144, no output) on 10-13 and 10-14; a build watcher watching itself for hours (09-11); three ssh launches killed because `bash $L/build_and_test.sh` shared the line with the bracketed pkill (09-23); a `while pgrep -f` wait spinning 47 min after the job ended (10-29). Count with `ps -eo pid,args | grep '[f]ake_tool.py' | grep -v "^ *$$ "`; wait with `&` and `wait`; a pkill goes in its own ssh call naming nothing else.

**Detached remote launch: `ssh host 'cd /x; (setsid nohup cmd < /dev/null > log 2>&1 &); sleep 1; ps -u $USER -o pid=,args= | grep cmdname | grep -v grep'`.** 11-02: `cd X && setsid nohup cmd ... &` hung three launches, since the `&` applies to the list and the subshell keeps the ssh stdout; `nohup` without `setsid` dies with the ssh (10-02). Read the ps; never relaunch on a timeout unchecked.

**One writer per build dir; poll remote pipelines with short ssh calls on status files; `stat` the binary against the source before believing a refusal.** 09-23 (#1675): two pipelines on `/var/tmp/kvand-land6`, and a binary older than its source from a half-applied tree (an edit script asserted midway; the unchained `git commit --amend; touch READY` ran anyway): 15/23 refusals and two phantom design flaws, 0 after a serial rebuild. Edit scripts: `set -e`, `&&`-chain, READY last.

**`git add` by name; run gpu_batch and boost tests from `/var/tmp`; before a push `git show --stat HEAD | grep -E "Bin|\.h5|\.dat"` must print nothing.** 09-23: `test_n2k_writeHDF5.yaml` writes `data/n2k_corr.*.h5` into the CWD, and `git add -A` sent 3.7 MB of HDF5 to PR #1675 (amended, 685e7c7c7).

**Judge a build by the compiler's own words and the artifact on disk; a compound command's status is the last command's.** 09-11: `cmake --build ... ; echo rc=$?; grep ... | head` reported 0 for `gmake: *** Error 2`. 09-14: `awk '{print $NF}'` on `/metrics` read timestamps (five counters all exactly 2004). Capture `rc=$?` at once, `grep -B2 -A3 "fatal error\|Error [0-9]"` the log, `ls` the artifact, use `$(NF-1)`, and different counters must differ.

**The CHORD open-item list is [CHORD_BUGLIST.md](../CHORD_BUGLIST.md) (closed items in [CHORD_BUGLIST_CLOSED.md](../CHORD_BUGLIST_CLOSED.md)); `airspy_docs/buglist.md` is the prototype's list in another repo and has never tracked CHORD.** Read the buglist first; do not reconstruct the list from `CHORD_GNSS_STATE.md`'s prose.

**Run the end-to-end harness before touching the chain: `scripts/gnss/e2e` (`scripts/gnss/site/build_tool.sh e2e`).** It injects a known code phase through the shipped acquire → seed → `propagate_seed` → despread chain and prints the error in chips at each hand-off (~28 s per PRN; `--skip-search` ~5 s), calling `gnssSeedTransport` rather than restating it.
